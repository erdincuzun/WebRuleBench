# WebRuleBench

[![tests](https://github.com/erdincuzun/WebRuleBench/actions/workflows/tests.yml/badge.svg)](https://github.com/erdincuzun/WebRuleBench/actions/workflows/tests.yml)
[![DOI](https://zenodo.org/badge/DOI/10.5281/zenodo.23142233.svg)](https://doi.org/10.5281/zenodo.23142233)

A benchmark environment for evaluating **LLM-generated web extraction rules**
(news article title/body/date/author/images/tags, and any fields you define in
a template) against human-curated ground truth. Rules can be **CSS selectors**,
**XPath expressions** or **regular expressions**: the LLM sees a cleaned
structural skeleton of *one* sample page per layout, writes one rule per field,
and the rules are then run — without the LLM — on every ground-truth page of
that layout, so both accuracy and generalisation are measured.

```
Raw HTML (data/dataset/raw/)
   │
   ▼
html_cleaner.py   — noise removal, 7 cleaning strategies
   │
   ▼
skeleton.py       — structural skeleton (tag + class + id; headings / short text in "enriched" mode)
   │
   ▼
llm_extractor.py  — one LLM call per layout, returns CSS / XPath / regex rules as JSON
   │                (backends configured in llm_models.json)
   ▼
rule_utils.py     — runs the rules (BeautifulSoup / lxml XPath / re on raw HTML)
regex_generator.py— optional CSS → regex conversion (REGEXN, extended)
   │
   ▼
experiments.py    — scores the rules on all ground-truth pages of the layout
reports.py        — leaderboards, breakdowns, CSV / LaTeX / PNG export, manifest
```

The **web application** (`webapp/`) covers the whole workflow in six
sections — data collection, templates & prompts, annotation, ground-truth
approval, LLM evaluation, reports & export — plus settings pages for LLM
backends and users. Several annotators write rules independently; an admin
compiles them into the approved ground truth using inter-annotator agreement
(Fleiss' κ) and content-level scores.

A user guide for the web application (Turkish) is in
[webrulebench/webapp/README.md](webrulebench/webapp/README.md); every section also has an in-app
**?** help in English and Turkish.

## Try it in two minutes (reviewer demo)

No LLM, API key or data is needed:

```bash
pip install -e .
webrulebench demo             # or ./run_demo.sh — builds demo/data/ on first run, serves http://127.0.0.1:5002
```

The login (user `reviewer`, admin) is printed and saved in `demo/data/REVIEWER_LOGIN.txt`.
With Docker: `docker build -t webrulebench . && docker run --rm -p 5002:5002 webrulebench`.

The demo (`webrulebench/demo/setup_demo.py`) creates a separate data folder and never touches real data:

- three synthetic news sites with different markup styles (semantic tags, CSS-in-JS hash classes,
  nested divs) — 31 pages, 5 layouts, generated by `webrulebench/demo/generate_pages.py`;
- rules of three annotators that differ in the three typical ways (only in writing, different
  selector for the same content, different interpretation of a field), so the GT approval page shows
  rule agreement and content scores diverging;
- an approved ground truth and a `demo` backend of type `replay` with two models: `demo-strong`
  and `demo-weak` (which makes typical LLM mistakes); new experiments and quick tests run instantly;
- ready results: a comparative experiment (strong CSS / weak CSS / strong XPath) and a regex run.

Suggested tour: **Ground Truth Approval → harborherald.example → Article** (K1 vs K2) ·
**LLM Evaluation → the demo group → Cross check** · **Reports → LLM results / Annotation & GT** ·
**LLM Evaluation → Quick test** with `demo-weak`.

## Data folder

All data (pages, annotations, ground truth, experiments, users, settings, `.env`) live in `data/` by
default; missing settings files are copied from `webrulebench/defaults/` on first start. Set `WRB_DATA_DIR` to use
another folder, and `WRB_PORT` / `WRB_HOST` to change the
address — e.g. `WRB_DATA_DIR=~/my-study WRB_PORT=5003 webrulebench serve`.

## Installation

Requires Python 3.10+ (tested on 3.10–3.13).

```bash
git clone https://github.com/erdincuzun/WebRuleBench.git && cd WebRuleBench
pip install -e .                 # installs the `webrulebench` command (`pip install .` works too)
# optional extras: pip install -e ".[fetch,mcp,figures,dev]"
playwright install chromium      # only with [fetch]: fallback for JavaScript-rendered pages
```

Without installing, run from the clone with `python -m webrulebench …` (`pip install -r requirements.txt`).
LLM backends are called over HTTP with `requests`; no vendor SDK is needed. For local models install
[Ollama](https://ollama.com) and pull a model, e.g. `ollama pull qwen2.5-coder:14b`.

| Command | |
|---|---|
| `webrulebench serve [--port 5001] [--data DIR]` | start the web application (= `./run.sh`, `python -m webrulebench serve`) |
| `webrulebench demo [--rebuild]` | reviewer demo on port 5002 (= `./run_demo.sh`) |
| `webrulebench users create-admin <name>` | first admin (also `list`, `create`, `reset-token`, `activate`, `deactivate`) |
| `webrulebench --version` | |

## Quick start

### 1. Start the web application

```bash
webrulebench users create-admin <name>   # first admin — prints a login token once
webrulebench serve                       # or ./run.sh
# open http://127.0.0.1:5001 and log in with the name and token
```

Further users are created from **👥 Users** in the app (or with
`webrulebench users create <name>`). Tokens are stored only as salted hashes.

### 2. Configure an LLM backend

Open **⚙ LLM Models**: five backends are preconfigured (`ollama`, `claude`,
`gemini`, `groq`, `nvidia`); API types are Ollama, Anthropic, Gemini and any
OpenAI-compatible endpoint. API keys can be entered on that page (written to
`data/.env`, never to `llm_models.json`) or exported as environment variables
(`ANTHROPIC_API_KEY`, `GEMINI_API_KEY`, `GROQ_API_KEY`, `NVIDIA_API_KEY`).
Use **⚡ Test** to check the connection.

### 3. Run the pipeline on a single page (command line)

```bash
python -m webrulebench.pipeline.skeleton data/dataset/raw/<domain>/article_001.html --show
python -m webrulebench.pipeline.llm_extractor data/dataset/raw/<domain>/article_001.html --backend ollama --rule-type css
python -m webrulebench.pipeline.llm_extractor data/dataset/raw/<domain>/article_001.html --backend ollama --rule-type xpath
python -m webrulebench.pipeline.llm_extractor data/dataset/raw/<domain>/article_001.html --backend ollama --rule-type regex
```

### 4. Score a rule on a page (Python)

```python
from webrulebench.evaluation.metrics import score_selector
from bs4 import BeautifulSoup

html = open("data/dataset/raw/<domain>/article_001.html", encoding="utf-8").read()
soup = BeautifulSoup(html, "html.parser")

# CSS ground truth vs. CSS rule (default)
score, label = score_selector(soup, gt_selector="h1.title", llm_selector="h1", field="title")

# CSS ground truth vs. an XPath rule — rule_type / gt_rule_type are independent
score, label = score_selector(
    soup, gt_selector="h1.title", llm_selector="//h1[@class='title']",
    field="title", rule_type="xpath", gt_rule_type="css", raw_html=html,
)
```

Full experiments (layout-based, comparative, cross-check) are run from the
**LLM Evaluation** section of the web application and summarised in **Reports & Export**.
The interface is in English by default; the **EN / TR** switch in the header changes it to
Turkish (translations in `webrulebench/webapp/i18n/`, see `webrulebench/webapp/i18n/README.md`).

## Repository layout

```
webrulebench/              all Python code (one installable package)
  cli.py                   `webrulebench serve | demo | users`
  paths.py                 code / data separation, WRB_* environment variables
  config.py                default news fields for the command-line tools
  users_store.py           users, hashed tokens, roles
  mcp_server.py            MCP server exposing the pipeline as tools (experimental)
  pipeline/                html_cleaner (7 strategies) · skeleton · llm_extractor (all API types incl. replay)
                           · llm_models (backend registry) · prompt_builder (prompt from a template)
  rules/                   rule_utils (CSS / XPath / regex runner) · regex_generator (CSS → regex, extended REGEXN)
                           · rule_agreement (normalization, observed agreement, Fleiss κ, Krippendorff α)
  evaluation/              metrics · experiments (layout-based, groups, cross-check) · reports (+ manifest)
  webapp/                  Flask app: core.py, routes/ (one blueprint per section), templates/, static/, i18n/,
                           manage_users.py
  defaults/                shipped templates, prompt variants, LLM registry (copied into data/ on first start)
  demo/                    reviewer demo: synthetic pages, demo data setup, test fixture generator
data/                      your data — not in the repository
demo/data/                 generated reviewer demo data — not in the repository
tests/                     unit and end-to-end tests, synthetic fixtures
paper/annotation_study/    inter-annotator agreement study: guideline, sample, analysis and figure scripts, results
pyproject.toml · CHANGELOG.md · CITATION.cff · LICENSE · Dockerfile · run.sh · run_demo.sh
.github/workflows/tests.yml  CI: ruff + pytest on Python 3.10–3.13
```

Code and data are separated: everything a user creates (pages, annotations, ground truth,
experiments, users, settings, API keys) lives in `data/`, which is not part of the repository.
`webrulebench/defaults/` holds the shipped templates, prompt variants and LLM registry; they are copied into
`data/` on first start. Synthetic test pages live under `tests/fixtures/`.

## Running the tests

```bash
pip install -e ".[dev]"
pytest -q          # 111 tests, incl. an end-to-end build of the reviewer demo
ruff check .       # lint (configured in pyproject.toml)
```

The tests are intentionally lightweight: they check the core formulas in
`metrics`, run every `html_cleaner` strategy and `skeleton` against a
handful of small sample pages under `tests/fixtures/`, check the CSS / XPath /
regex runners, verify that `score_selector` behaves consistently against
the approved ground truth for those pages, check experiment scoring, the
agreement statistics (rule normalization, Fleiss' κ, Krippendorff's α — also
that the browser copy in `static/compile.js` normalizes identically) and the
translation catalogs.

## Security note

Login is username + token, with tokens stored as salted SHA-256 hashes and
role-based access (annotator / admin). The application is intended for a small,
trusted group on an internal network and is not designed for public-facing
deployment.
